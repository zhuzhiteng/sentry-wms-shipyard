船厂业务位于独立 `shipyard` 领域，通用 WMS 的认证、仓库、区域、用户、
审计和基础库存能力仍作为技术基座使用。

## 当前业务闭环

1. 管理端维护船号、工程号、制作图绑定与区域船号定置。
2. 导入到货清单，预览字段、重复行、缺失字段和区域冲突。
3. 确认清单后生成票货和待收货任务。
4. 小程序逐托拍吊牌，本地优先 OCR 识别字段，原图留证。
5. 服务端强校验物料编码、品名、规格、绑定关系、托组后缀和数量。
6. 收齐整票托盘后按实收入库；少件保留待补状态，补货累计补足。
7. 管理端同时支持船厂正式出库清单、日配送/按需需求和急单/改单派工单。
8. 日配送与急单按工程号/船号、托盘号/制作图号匹配仓内整票；无货行保留，
   补货后可重新匹配，不伪造库存。
9. 小程序逐托拍吊牌，整票齐套后一次扣库并记录流水。
10. 全部票货完成后确认装车，形成原图、OCR、操作人和时间链路。
11. 到货票货可标记“顺延下批”；四联验收单保留工厂联、船厂联和仓库复印件
    的流转记录。

## 现场约束

- 不使用二维码、条码或扫码设备；
- 不解析或保存工厂二维码内容；
- 唯一现场端为原生微信小程序；
- 一张吊牌只拍一次，原图同时用于留证和 OCR；
- OCR 结果不能直接落库存，必须通过服务端字段校验；
- 同一请求重试不能重复收货、扣库或装车。
- 客户端在结果未确认时必须复用原幂等键，不能重新生成提交编号。
- OCR 默认使用 API 主机内的 RapidOCR，百度只作为显式配置的可选主服务或兜底；
  启用百度时图片会发送到百度云。

## 验证原则

- 数据迁移必须覆盖全新空库、已有旧结构升级和重复执行；
- 船厂收货、出库、权限和跨仓隔离使用独立 `sentry_test`；
- 管理端测试必须在干净依赖树执行，生产构建必须通过；
- 小程序测试覆盖一次拍摄、OCR 必填、多托齐套、幂等和错误恢复；
- HTTP E2E 覆盖登录、配置、清单、收货、出库、装车、照片字节和数据库不变量；
- 独立测试库完成 custom dump、双库恢复、逐表行数一致、088/089 双轮执行和恢复库 API 启动；
- 新增生产运维 overlay：主动监控 API/DB/Redis/Celery/备份状态并发送去重告警；
- 新增 PostgreSQL 16 兼容的定时备份、归档校验、SHA-256、保留与失败重试；
- 依赖审计、密钥扫描、Ruff、Bandit、`git diff --check` 均为交付门槛。
- OCR provider 抽象必须分别验证本地和云服务，验收报告不得把兜底结果混为单一
  provider 的准确率。

自动测试中的 OCR 通常是确定性 stub。它证明事务、字段校验和证据链路，不证明
RapidOCR 或可选百度兜底对现场吊牌的识别率。

## 当前发布结论

代码、自动测试和模拟流程通过只说明研发侧可交付，不等于生产可用。以下事项仍需
外部条件与现场证据：

- 扩充 RapidOCR 真实现场样本和识别率验收；启用百度时另行完成云样本、计费和隐私验收；
- 微信 AppID、HTTPS 合法域名、隐私声明和 iOS/Android 真机验收；
- 真实船厂吊牌、弱网、上传中断和重复操作演练；
- 实际配置 HTTPS 告警端点，完成故障/恢复通知验收；
- 在生产同构环境完成首次计划备份和隔离恢复；
- 迁移窗口、回滚演练和仓库/船厂 UAT。

在上述事项完成前，生产结论保持 `NO-GO`，且不得虚构部署、真机或业务验收结果。
